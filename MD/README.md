Written for: the Asset Lifecycle team, as a map of where things are written down and how change tracking works.

## 1. The MD files

Everything lives in `MD/` except `readme.md` and `SETUP.md` (repo root) and `CHANGELOG.md` (generated, never hand-edited).

### Start here
| File | What it is |
|---|---|
| `readme.md` (root) | Front page: what the project is, layout, how to run, mocked users |
| `SETUP.md` (root) | Setup and run guide, including the Node 22+ requirement |
| `MD/ASSET_LIFECYCLE_MASTER.md` | The master reference: data model, service, roles, apps, current state |
| `MD/intent.md`, `MD/prd.md` | What the system is for, and the product requirements |

### Design and architecture
`architecture.md` (layers, services, security), `flow.md` (asset lifecycle state machine), `deployment.md` (what changes from local dev to BTP), `frontend.md` (the ten UI5 apps).

### Registers and logs (the "why" of the project)
| File | What it records |
|---|---|
| `decisions.md` | Every design decision as `DEC-NNN` with the reasoning |
| `bugs.md` | Every bug found: open, fixed uncommitted, fixed (with the build or InBul id) |
| `tasks.md` | Living task tracker with `[ ]`, `[/]`, `[x]`, `[~]` |
| `tried_and_implemented.md`, `tried_and_failed.md` | What worked and what didn't |
| `pain.md` | What can break the system and how badly |
| `rules.md` | Working rules for the project |

### Session handovers
`session_handover_YYYY-MM-DD.md`, one per working session.

### Evidence
`snapshots/` (repo root): screenshots of the running frontend, indexed in `snapshots/README.md`.

### Generated
- `CHANGELOG.md`: build history, regenerated by `scripts/changelog.mjs`.
- `MD/builds/build-N.md`: one report per build.

## 2. Builds

A **build** is a numbered, user-visible release: anything that shows up in the app or dashboards.

- Numbers start at **1000** and rise by one. None exist yet; the first will be **Build 1000**.
- The number is pinned by a git tag, `build-1000`. The **tag is the source of truth**. Never put "(Build N)" in a commit title, and never renumber or move a tag.
- Look one up with `git show build-1000`, or compare two with `git diff build-1000 build-1010`.
- Every build has a report, `MD/builds/build-N.md`:
  - a hand-written part (what changed, why, how it was verified, what to improve next), written once and never overwritten;
  - a "Files changed" list that is rebuilt from git each time.

### The commit flow (from `scripts/changelog.mjs`)
1. `git add` the change files first. The report's file list reads the staged diff.
2. `node scripts/changelog.mjs --pending "<title>" "<one or two plain sentences>" --why "..." --verified "..." --next "..."`
3. `git add MD/builds CHANGELOG.md`, then commit with the same title and a real body (what, why, verified).
4. `node scripts/changelog.mjs --tag` pins the number. It doesn't modify files.

`node scripts/changelog.mjs --changelog` regenerates `CHANGELOG.md` alone.

### Batching rule
Don't make a build for every small fix. Wait until about **10 fixes** pile up, then make one build of all of them. This applies even to one urgent fix. Push only when explicitly told to ("push"). Push tags too. Commits carry only the user's name, with no co-author trailers.

## 3. InBuls

An **InBul** is an internal change: docs, bookkeeping, tooling, scripts, anything the app doesn't show.

- Commit titles start with `InBulNN:`, for example `InBul1: Add MD documentation set and changelog script`.
- Print the next id with `node scripts/changelog.mjs --next-internal`.
- Skip `--pending`. Commit, then run `--tag` to pin an `InBulNN` tag.
- InBul commits get **no build number**, no CHANGELOG entry, no report.
- A merge that brings other work back in is also an InBul. Its work is already counted in the build it came from.

### Build or InBul?
| Change | Label |
|---|---|
| Shows in the app or dashboards (UI, service behaviour, data model, access rules) | Build |
| Docs, MD updates, scripts, tests, tooling | InBul |

## 4. How the pieces connect

```
change made
   ├─ user-visible ──> Build N ──> CHANGELOG.md entry + MD/builds/build-N.md + tag build-N
   └─ internal     ──> InBulNN ──> commit + tag InBulNN only

why it was done ──> decisions.md (DEC-NNN)
bugs found/fixed ──> bugs.md (cites the build or InBul that fixed it)
current state    ──> ASSET_LIFECYCLE_MASTER.md and the topic docs
```

A build report says **what changed**. `decisions.md` says **why it was designed that way**. `bugs.md` links each fix to the build or InBul that carried it. The master reference and topic docs describe **how things are now**.
